## 结论与证据强度

无线已有证据证明：异常发生时，发送端声明的尺寸和接收端解码帧都是方形，窗口只是跟随该画布。原画协商应优先做对照实验。当前下游还缺少独立的有效内容区域；仅调整窗口比例不足以解决帧内填充。

有线的方形能力声明也存在，但不能直接套用无线结论。已有 iPad 原生 B 实测依赖较大的方形能力才能避免降分辨率。用户本次反馈涵盖有线，然而尚缺同一问题会话的有线原始帧、格式扩展和方向元数据，不能宣称两条链路已确定为同一原因。

## 当前代码如何处理尺寸

1. [WirelessReceiverService.cs](../../src/App/Services/WirelessReceiverService.cs) 中原画监听能力统一为 `2880×2880`。`ReceiverCapabilityFor` 不再使用机型匹配尺寸启动接收器；旧 native 保存值也迁移为统一原画。该行为引入于 `1be6588`（2026-11-10）。目标是让后连接的大屏设备不受首台小屏设备限制。
2. [CaptureSession.cpp](../../src/Core/src/Capture/CaptureSession.cpp) 中普通有线 B 将请求转成长边方形；原生 iPad B 默认至少 `4096×4096`；爱思模式固定 `1565×1565`。这些是协商请求，不能当成收到的真实分辨率。
3. 无线 [WirelessReceiverHub.cpp](../../src/Core/src/Capture/WirelessReceiverHub.cpp) 保存 source/output 几何用于诊断，发布尺寸仍以完整解码帧为准。有线 [CoreMedia.cpp](../../src/Core/src/Media/CoreMedia.cpp) 解析 `vdim` 与编码参数、每帧方向，尚未提供 clean aperture / 像素宽高比 / 有效内容矩形。
4. [DecodedFrame](../../src/Core/src/Media/MediaFoundationDecoder.h) 只有帧宽高，缺少独立可见区域。[D3D 渲染器](../../src/Core/src/Renderer/D3D11PreviewRenderer.cpp)、[独立窗口](../../src/App/Windows/NativePreviewWindow.cs)、[截图](../../src/Core/src/CoreApi.cpp) 和 [坐标映射](../../src/App/Services/PreviewCoordinateMapper.cs) 都使用该完整宽高。

因此需要区分：接收能力、压缩/解码画布、画布中的有效内容和窗口客户区。修改其中一层的数值，不会自动改变其它层的像素。尤其不能把 `2160×2160` 的缓冲区直接改报为 `2160×994`，否则像素布局和点击坐标会错误。

## 上游核对

使用 ego-browser 核对 UxPlay 上游，固定参考提交 `48f5ce47c9ef694afccfac907c9e8828329657fe`：

- [raop_rtp_mirror.c](https://github.com/FDH2/UxPlay/blob/48f5ce47c9ef694afccfac907c9e8828329657fe/lib/raop_rtp_mirror.c#L554-L606) 读取 codec 包头的六个浮点字段：40/44 为 source 宽高，48/52 为 x/y offset，56/60 为 output 宽高。项目现有几何事件只保留四个宽高，本地旧版 UxPlay 还把 48/52 标为 unknown。
- [video_renderer.c](https://github.com/FDH2/UxPlay/blob/48f5ce47c9ef694afccfac907c9e8828329657fe/renderers/video_renderer.c#L1070-L1082) 记录六字段，但未用 offset 自动裁切。因此这些字段值得采集，不能仅据命名就认定已经获得可信裁切矩形。

## 推荐的实施顺序

### 先对照原画协商

无线在同一构建、同一设备、同一页面、同一接收后端下依次测试：

| 候选 | 目的 | 必须保留的判断边界 |
|---|---|---|
| `2880×2880@60` | 复现当前基线 | 方形帧不自动表示画面被拉伸 |
| 匹配机型长边方形，例如 `2622×2622` | 重现曾经正常的机型档 | 只作为对照；首台设备决定全局能力会限制晚加入的大屏设备 |
| `5120×2880@60` | 保留当前 2880 高度上限，并对照较宽的显示目标 | 原生 Host 参数白名单已接受该尺寸，托管设置校验仍需实验入口；尚无本次真机成功证据 |
| `1920×1080@60` | 验证同场景在普通档是否正常 | 属于降档对照，不能作为原画修复验收 |

`3840×2160` 会降低当前竖向能力上限，不优先作为原画方案。矩形能力也只是实验候选，不能预先断言一定恢复面板像素。

每项同时记录首连竖屏、首连横屏、左右横屏、返回竖屏；分开测试 Original 和 UxPlay。收集实际解码尺寸、原始 PNG、codec header 六字段及 SPS 中的 crop / SAR 信息。对照完成后再决定默认能力，而不是直接回退旧配置或在旋转时重启接收器。

最终候选必须补测“两台设备，小屏先连、大屏后连”，避免为了单机恢复而重新引入全局能力限制。实验过程的切档重连不能混入正常旋转的稳定性结果。

有线普通 B、原生 iPad B 和爱思模式分别记录 HPD1、`vdim`、格式扩展、帧 PTS 和方向、转正后的 PNG。先复现，再分别决定是否需要修改协商。保留已有原生 iPad 能力，避免清晰度降档或旋转断流。

### 再补可信的有效内容区域

若协商调整后源帧仍必须使用方形画布，则检查协议、SPS/解码器 aperture 是否确实提供有效区。方向与有效区都应随对应帧/PTS 生效，避免新横屏区域被套到队列中的旧竖屏帧。

实现时优先在发布帧前统一处理有效像素与展示宽高，让主预览、独立窗口、截图、录制和反控继续使用同一份几何；保留源画布尺寸作诊断。硬件帧需保持 GPU 路径，避免为了检查黑边而每帧读回并复制整幅画面。纯软件无缩放裁切可以减少外部黑边，但不能恢复源端已经损失的清晰度。

目前不能依据面板比例或单帧亮度自动裁边：暗页面、合法方形内容和电影本身的黑边都可能被误裁。旧 `padded_content_orientation` 只是未调用的粗采样启发式，不能直接升级为生产裁切。缺乏可信元数据时，应先用真实原帧序列验证稳定性和误判率，再决定是否加入受限回退。

### 测试版采用的处理

上述结果没有证明把原画能力统一改为矩形即可解决问题，因此测试版保留既有无线 `2880×2880` 和各有线模式的协商默认值。新增诊断覆盖仅在明确进程环境变量存在时生效，不写入设置：

- 无线 `IPHONE_MIRROR_DIAGNOSTIC_ORIGINAL_CAPABILITY`：`square`、`wide`、`native:<精确 ProductType>`，只作用于原画；普通画质不受影响。
- 有线 `IPHONEMIRROR_DIAGNOSTIC_USB_DISPLAY_WIDTH` / `HEIGHT`：成对十进制 16–8192，演示模式忽略；原生 B 二次配置和回退保留实验值。
- MF 输出格式选定时记录 frame / PAR / 三类 aperture，不凭这些新日志直接裁切。

共享 [ScreenContentGeometry](../../src/Core/src/Media/ScreenContentGeometry.h) 在发布帧前统一处理已确认的方形填充画布：

1. 必须有精确机型和已知面板比例，且同一连接已观察到至少三帧匹配比例的原始矩形镜像。非匹配矩形撤销旧参考，新连接也清除参考。
2. 仅检查有完整 CPU 像素的偶数方形 SDR NV12/P010，GPU 帧不读回。分别验证按历史实际帧比例推导的两个居中方向；不直接套面板像素放大。
3. 逐像素检查拟丢弃区域的黑色亮度和中性色度，区域内四边的亮度信号须充分分布；同一区域至少三帧、跨度至少 100ms 才首次确认。
4. 只做原始像素复制，不缩放、不转置。确认后的暗场保持区域，外围仍逐帧完整检查；任何外围信号立即恢复完整画布。未确认的黑屏不推断区域。
5. 无线每客户端独立保存状态；有线只在确切机型的非演示会话启用，并在正确的帧方向转换后处理。协议会话重建清理参考，普通格式变化保留参考。

处理后的像素与宽高作为同一帧发布，因此主预览、独立窗口、截图、录制和归一化输入映射共同跟随；编码源尺寸保留在日志中。新增 `wireless_active_area` / `usb_active_area` 仅在状态变化时记录，不把裁切后尺寸称为源端原生分辨率。

这是有严格前提的像素回退，并非来自协议的权威有效区。真实方形内容若与手机屏幕比例和填充像素完全一致，仍可能无法单凭像素区别；因此保留这一测试边界，不能声称所有外接视频已经兼容。横屏首连始终只有方形、未知机型、奇数方形（包括部分爱思输出）、暗画面无法建立初始边缘证据、HDR 和纯 GPU 帧均保留原帧。演示模式不启用该处理。测试版解决目标是已正常镜像后切入可验证的方形填充，不宣称所有非演示场景或源清晰度问题均已真机解决。

独立 [几何专项测试](../../src/Core/tests/ScreenContentGeometryTests.cpp) 覆盖像素/色彩/时间戳保持、完整外围核验、误裁拒绝、暗场、缓冲布局、时间稳定、状态清理和设备隔离；Core 另用实际 `WirelessClientStream.publish_video` 验证三帧参考、方形到矩形发布、所有预览共享帧、立即撤销及重连隔离。真实有线和新增回退的设备验收仍待用户有空复测。

## 仿真边框的左右横屏

用户截图中，原生横屏画面里的灵动岛在左侧，边框按固定顺时针方向绘制，因而在右侧生成了另一个开孔。第七候选使用当前帧对应的物理朝向和窗口局部旋转来计算边框方向。有线原生 AirPlay 使用与该帧匹配的 SpringBoard 姿态。普通 QuickTime 在输入画布为竖屏且携带旋转字段时使用该帧的旋转。有线预转好的横屏和无线已转正帧都可以根据画面中的居中开孔位置区分左右。方向不明时保留横屏外框，并让画面覆盖仿真开孔区域。反控点击和键位取点读取预览实际呈现的边框方向。
