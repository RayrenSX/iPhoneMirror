# Issue #88：广告交接与短视频播放审查（2026-11-17）

本轮在 `main` 工作目录修复，保留其他未提交改动。没有创建分支或工作树。远端获取尝试因直连重置、原本地代理未监听而失败，未执行覆盖本地改动的同步。

## 已确认的问题与修复

- 原生通知只凭 rate=0 推断暂停，缓冲、跳转和打开资源时也会误发暂停。新增明确的播放状态，通过 C#、Core、IPC、WirelessHost 和原生回调传递，播放信息的就绪、缓冲标志随状态变化。
- 通知使用控制命令编号去重，音量等命令会重复触发同一视频的状态甚至结束通知。现使用独立的视频编号，并将状态和播放信息限定到当前视频所属会话。
- 已完成的视频可被迟到的回调、时长发现或恢复继续任务改变。现保留终态、冻结实际位置，取消定时器及旧恢复；保留投放会话以接收下一段。
- 提前结束保护原来随控制命令编号增加而重新获得恢复机会。现按一次播放尝试限制恢复，不把未播放的短广告报告为完成。失败后允许明确的重播/跳转开启新尝试。
- 延迟恢复可能在新跳转后覆盖新播放器。接受实际跳转时现使旧恢复失效。
- WMF 的唯一 EOF 回调可能早于 FFmpeg 退出，被忽略后再无检查。现进行有限复查，并为生产进程已退出、实际位置持续停滞的情况补充检查。
- 重复真实播放还复现了 1 秒视频在 EOF 前将 Position 从约 0.99 秒回退，覆盖已采集进度并误触发恢复。现保留当前播放尝试已观察到的最大实际位置；新视频、实际跳转重置记录。EOF/失败在关闭状态前冻结该位置，防止恢复又按经过的时间推进到结尾。短片尾差容限包含 250ms 采样和一帧余量。
- 恢复预算原来仅凭 MediaOpened 之后经过的时间重置。现同时要求实际位置持续推进，冻结不能无限重置预算。
- 选中的视频分支仍保留八种语言音轨，FFmpeg 会全部探测，并可能选择第一种德语音轨。现只保留发送端默认音轨，按 DEFAULT、AUTOSELECT、首条顺序回退。
- 所有控制连接断开后重用 Session-ID，请求编号原来从 1 开始；旧响应可误填新会话请求。现请求编号跨会话实例保持唯一，并增加连接交接和取消回归。
- 本地播放连接中断后原桥接会把余下的前向 TS 数据交给新连接，丢失已读取的头和帧。现将该流标为失败并重建，HEAD 和未消费数据的探测仍可安全重试。
- 真实 WPF 回归复现：同一份 3.2 秒 TS 经文件和有 Content-Length 的 HTTP 均可播放，经原桥接完整送出却在打开前报 C00D11B1。仅改成 chunked 仍失败。修复采用有上限的启动缓冲，小的有限资源确认 EOF 后提供准确长度，较大/直播资源继续流式发送；不使用整段磁盘缓存。
- combined 接收模式的 /server-info 与镜像端能力策略不一致，仍会宣告视频交接能力。现与独立视频端的角色划分保持一致。

## 日志结论的边界

原会话中，404 出现在手机关闭全部连接后、UI 才处理旧 Play；410 紧跟最后连接关闭；504 是资源请求发出后 15 秒没有收到 FCUP 响应。没有加入掩盖会话关闭的无限重试，也不把这些旧状态码单独作为活跃资源仍损坏的证据。
