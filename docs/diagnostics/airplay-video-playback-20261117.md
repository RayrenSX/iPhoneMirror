# AirPlay 视频播放与续集交接

本页合并 2026-11-17 的 Issue #88 连续修复记录，保留确定的根因、约束与验证边界。当前操作见[使用指南](../USER_GUIDE.md#视频应用投屏)，运行库来源和补丁见[来源记录](../../third_party/airplay-server/SOURCE.md)。

## 确定问题与处理

| 范围 | 结论与处理 |
|---|---|
| 自然结束 | 外部 HLS／直接 MP4 曾在自然 EOF 时停止整个会话。统一报告当前项目 Completed，保留会话供手机发送下一集；错误、用户停止与提前 EOF 不冒充自然完成 |
| 终态与重播 | 明确区分 Playing、Paused、Completed、Failed；已完成项目不被迟到回调复活。Seek／Resume 开始新播放尝试，保留音量、静音和目标位置；旧恢复不能覆盖新跳转 |
| 广告通知 | 按视频实例和会话归属隔离通知，不能用 rate=0 推断暂停或用通用控制命令编号去重。确认、拒绝和连接关闭分开诊断 |
| `/scrub` | GET 返回真实 duration／position，不能触发跳转。POST 严格解析以秒为单位的 position，拒绝空值、非法值、重复参数及其他会话；保留合法 Seek0 |
| 有限短片 | WMF 对未知长度响应可能在打开前返回 C00D11B1。已知短片在实际 EOF 后发送准确长度，内存预读保持 512 KiB，超过部分使用有界临时文件，结束或失败后清理；直播不无限缓存 |
| 启动预算 | 桥接和窗口共用有界启动预算，有效探测／媒体进度才能延长空闲等待；旧事件不能复活超时尝试。慢网络及多路输入不能各自无限重试 |
| 分离音视频 | 周期重置的 fMP4 在旧交错策略下曾卡住。按共同起点同步并限制交错，验证真实位置和完整帧，不能只提高阈值或用保留的最大位置证明连续播放 |
| 资源与输入选择 | 优先发送端默认音轨；跨连接请求编号保持隔离。消费过的前向流不能把残余 TS 当成新资源重新发送 |

## 验证与边界

- 历史回归覆盖真实 FFmpeg、HTTP/HLS、WPF 播放、加密控制连接、进度读取／跳转、提前 EOF、失败后重播、会话隔离和有限恢复；使用合成媒体的测试不等同于所有手机视频 App 的队列实现。
- 旧接收器可复现非法 GET `/scrub?position=bad` 触发 Seek0；修复后只允许合法 POST 跳转。它证明了路由缺口，不能证明旧会话每次归零都是解析错误。
- 周期重置的分离 fMP4 在修复后通过约 60 秒连续播放测试；这是特定素材和环境的结果，不是所有网络的时延保证。
- 用户确认爱奇艺续集通过；对应日志在 13:11:30 收到本集 Completed ACK，13:11:32 收到手机下一集 Play，13:11:38 打开新集。随后停顿对应明确的本地暂停，不是自动恢复。
- 最初连接需要重试、YouTube 广告队列、其他来源及长期弱网行为仍需各自实机验证。测试夹具主动发送下一次 Play 不能作为手机自动接续证明。

原始日志与交付哈希是当时的本机产物，不随仓库分发。复现入口以 `src/App.Runtime.Tests/MediaCastDiscontinuityTests.cs`、`src/App.Logic.Tests/FcupHlsPlaybackTests.cs` 和当前协议测试为准；本次合并未重新执行这些实机或媒体测试。
