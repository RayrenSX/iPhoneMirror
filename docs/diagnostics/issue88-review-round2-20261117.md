# Issue #88：续集通过后的第二轮审查

用户已确认爱奇艺可以自动接下一集，随后要求继续审查和修复。本轮在集成 `main` 中审查媒体完成、失败、重播及 DLNA 控制/通知的并发边界。

## 实机结果

上一交付 `issue88-iqiyi-next-20261117` 的日志确认：13:11:30 本集 Completed 获得手机 ACK 200，13:11:32 手机发送下一集 Play，13:11:38 下一集打开。此后 1.430 秒停留对应本地明确暂停。该闭环和用户反馈一致，详见前一轮报告。

## 复现与修复

普通 HTTP MP4 自然完成后，应用已将 `_mediaOpened` 清除；重播路径又要求媒体已经打开，导致 Resume 或终态 Seek 无法创建新播放。直接媒体的错误入口还会请求停止整个会话，不能保持 Failed 并重试。修复为在可重播终态准备新播放器，保留音量、静音和播放意图，打开后再应用目标位置；本地时间轴也必须经过同样的终态判断。错误以失败项目状态上报，用户仍可明确重试。

真实专项还发现：暂停的新 HTTP 播放器在首次设置 Position 后再 Pause，会把位置重置为零。现在先保持暂停，再应用初始目标位置。严格验证真实位置到达目标且未自行播放，没有仅按界面目标值放行。

外部 HLS 的重连次数耗尽原先会停止会话，FCUP 才保留失败状态。现在两类桥接 HLS 都结束为 Failed，保留实际观察位置并取消旧恢复任务，避免取消发送端队列。

原生控制端在 Completed/Failed 后收到 Pause，会把状态改为 Paused；应用再次上报终态可能形成重复结束通知。暂停应保持已有终态，明确 Seek/Resume 才进入新的播放尝试。

DLNA 的结束通知、同一项目的 Seek/Resume 和 GENA 发布存在竞争。同步必须同时核对当前命令及渲染器代次；控制请求在更新渲染器状态后、抵达原生回调前的窗口也需要失效保护。本地重播的非终态状态应同步恢复 DLNA 传输状态。事件的状态快照、SEQ 和网络发布顺序必须一致，且不能持有播放状态锁等待网络。

SOAP 控制命令的状态修改和原生回调另用命令锁串行，防止较早 Seek 的回调晚于新 Play 而覆盖新项目。接收端停止请求也在核准当前命令的同一临界区内提交对应传输状态，通知在锁外发布。来自已被 AirPlay 接管的旧 DLNA 控制请求不能停止或修改新来源。

HTTP 解析器原先拒绝合法的重复 Accept/Connection 列表字段。修复只合并明确的列表字段；Host、Content-Length、Transfer-Encoding、SOAPAction 等字段仍保持严格判断。读取结果新增有限原因与接收字节数，空 TCP 关闭和正常停止不计解析失败，日志不包含请求地址、头值或正文。64 KiB 请求头边界按头部结束位置判断，独立于已接收正文大小。

## 验证边界

新增用例先对旧产品复现失败，再验证修复。真实 MP4 测试使用本地 HTTP、WPF 解码器与变化画面；错误回调测试在实际 MP4 已打开后触发 WPF 的同一错误处理入口。并发回归使用受控阻塞确定性地检查旧完成通知与新控制请求的交错。

此前手机首次连接需要重试的现象尚未取得明确请求证据，不能把重复请求头修复直接认定为其原因。新诊断将在该现象再次出现时区分空连接、超时、畸形请求和关闭。

最终通过的测试、交付路径及哈希记录在新交付的 `BUILD-INFO.json`。

普通 MP4 的两个真实播放专项共十二项通过，覆盖 Completed/Failed 后 Resume、本地与远程 Seek、迟到旧回调、静音/音量和暂停意图；零停止请求，首尾画面变化。错误路径在实际媒体播放后注入真实 WPF 错误回调参数，不能等同于模拟所有网络损坏形式。

GENA 使用独立的全局发布锁保证快照、序号和发送顺序；播放状态锁不跨网络。慢订阅仍会延迟其它订阅通知，这是本轮保守串行实现的已知成本，未进行通知吞吐优化。
