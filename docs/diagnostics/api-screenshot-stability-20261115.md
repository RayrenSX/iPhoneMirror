# 高频 API 截图与有线反控稳定性排查（2026-11-15）

## 已核实的现象

用户反馈为 10–15 台有线设备，自动化 API 高频截图时反控更容易断开，部分场景连投屏也断开；手动重连反控可恢复。

提供的 `reverse-control.zip` 内反控日志显示：一个桥接进程先出现 `SSLError`，随后反复报告 `bad mux length 2426763216`，三次自动恢复均失败，其他设备的桥接进程仍正常。日志没有截图端点记录，因此不能直接认定这些错误全部由截图引起。

本地三台设备测试补充了更直接的证据：原有 64 KiB 读取路径下，一条反控流的下一个序号比预期多 89 字节；随后再次发生 mux 包边界错位。新增的恢复逻辑在保留 USB 读取线程和设备配置的情况下完成了恢复，投屏没有中断。仅改为 16 KiB 后仍出现过序号缺口，读取尺寸并不是完整解释；序号缺口也不能单独证明数据永久丢失，必须允许乱序数据补齐。

[上游 usbmuxd 的 usb.h](https://github.com/libimobiledevice/usbmuxd/blob/master/src/usb.h) 明确区分 16 KiB 的单次 USB 读取上限 `USB_MRU` 和完整 mux 包上限，并指出更大的读取请求会被底层分片，带来竞态等问题。本项目此前把完整包上限 64 KiB 用作单次读取大小。调整读取尺寸修复了这项分片风险；不能由此断言所有 USB 或 SSL 错误均来自同一原因。

[libusb-win32 的同步读取实现](https://github.com/mcuee/libusb-win32/blob/master/libusb/src/windows.c) 在超时时取消读取；本地使用的是 libusb0 后端。原 200 ms 的轮询短于约 800 ms 的常规剪贴板/健康流量间隔，因此另外将读取等待调整为两秒，减少正常空闲时的取消。取消边界竞态与实际缺口的关系仍需结合真机结果判断，不能把这个推断当作已证实的唯一根因。

## 改动

- API 截图在目标解析之前合并同一设备的并发请求，最多两个编码任务、32 个待处理设备；排队两秒后限流，操作十秒后超时。
- 客户端取消不会取消其他等待者。已执行的任务和未结束的取消清理继续计入容量；取消回调缓慢也不会阻止请求按时返回。
- 使用原始分辨率、无损 PNG 的快速编码路径，减少完整位图中间副本。独立解码校验了像素、透明度、奇数尺寸、行填充和多 IDAT 数据块。PNG 文件可能比 UI 保存截图更大。
- 校验帧布局、读取超时和投屏会话更换，异常返回明确的截图 503，不误报为反控输入超时。
- 已有投屏会话短暂没有可用帧时，在同一个合并任务内最多等待 500 ms，并重新解析尺寸；不启动或重启投屏，不返回旧 PNG。尺寸刷新不会误判为会话关闭，真正关闭或持续无帧仍会失败。
- USB 单次读取改为 16 KiB，完整 mux 包仍支持 64 KiB，由解析器组装分片。
- 坏包后按协议包标识重新寻找边界，保留跨读取的半个包头，限制残留缓冲；不再反复解析同一个坏包头。主机和设备方向的两种包标识均有覆盖。
- TCP 重复或重叠数据不会重复送入 TLS；处理序号回绕、FIN 和异常 TCP 头。提前到达的数据在最多 64 段、128 KiB 的缓冲内等待补齐，只确认连续字节；三秒未补齐或超出窗口才终止受影响的逻辑流，避免继续交付损坏记录。
- 上述包恢复不释放或重新认领 USB 接口，不切换 USB 配置，不发送第二次 VERSION 握手，也不重置设备。
- 请求日志增加方法、端点和取消状态；反控诊断保留 SDK 已消费的 TLS 错误原因，不记录屏幕或 TLS 数据内容。

## 验证

运行时测试构建通过，零警告、零错误。Automation API 集成测试通过，包括 15 个模拟截图源、并发合并、有界队列、十秒超时、200 次完成与取消竞态、缓慢取消回调、会话更换及 PNG 独立解码。

Python 相关测试共 183 项通过：mux 流 16、有线恢复 52、反控逻辑 90、Lockdown 清理边界 12、桥接安全 7、打包钩子 1、自动化剪贴板 5。mux 测试包括最大包的 16 KiB 分片组装、用户日志同款异常长度、所有包头切分点、重复/重叠与乱序数据、乱序 FIN、有界补包等待及保持原 USB 线程和接口。

最终真机使用三台设备，同时开启有线投屏与反控，投屏尺寸分别为 1082×2340、2360×1640、1206×2622。测试客户端校验每张 PNG 的结构和 CRC，不保存屏幕内容，不发送触摸或键盘输入。

## 范围

本地覆盖三台设备，不等同于已经复现并验证用户的 10–15 台设备、USB 集线器和长期运行环境。保留诊断和复测脚本，便于在该环境中核对是否还有丢字节、坏包、自动恢复或投屏重连。

当前构建来自本仓库 `main` 的整合工作区，交付目录为 `outputs/iPhoneMirror-main`。测试进程已正常退出，临时截图限额从 30 恢复为原来的 5 次/秒，API 持久配置仍为关闭；只移除了新增的测试 iPad 绑定，保留原有三个绑定及其他现有配置。多设备客户复测时需要按实际请求量调整截图限额，15 台各每秒一次截图需要至少 15 次/秒的预算。

验证期间清理了约 29 GB 历史构建产物，当前 C 盘可用空间约 34 GB。约 355 MB 的重复发布暂存文件删除被自动审批策略拦截，已保留，没有改用其他方式删除。
