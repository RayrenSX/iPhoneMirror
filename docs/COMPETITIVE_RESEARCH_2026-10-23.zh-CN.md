# iPhoneMirror 同类项目调研与功能建议

调研日期：2026-10-23。基线为当天本地工作区，包含尚未提交的改动；不能等同于公开发布包。

本次阅读了项目 README、使用教程、路线图、API 文档及相关实现，并查询同类项目官方网页、官方仓库和本项目公开 Issue。未安装竞品或进行延迟、画质、设备数量实测。下文的工作量仅表示相对复杂度，不是交付工期。

## 结论

iPhoneMirror 已具备完整的投屏与输出链路。最值得投入的方向是：让用户更容易连上、更容易定位问题、更容易恢复常用工作环境，并让现有自动化能力更容易被外部工具调用。

建议下一阶段优先做三个可独立交付的功能：

1. **连接健康检查与脱敏诊断包**：降低驱动、DDI、蓝牙、无线故障的排查成本。
2. **多设备布局和使用场景预设**：把现有独立窗口、设备绑定、画质设置组织成可恢复的工作环境。
3. **可靠录制模式**：分段保存、异常退出后恢复、磁盘空间预警。

如果更偏向 AI 工具和自动化用户，可将第 3 项替换为**仓库内维护的 MCP 适配器及客户端配置向导**。

## 二、同类项目有什么值得学

| 项目 | 官方资料中值得参考的能力 | 对 iPhoneMirror 的启发 |
|---|---|---|
| [scrcpy](https://github.com/Genymobile/scrcpy) | 快速启动、简洁界面、细致的连接/音视频选项；录制复用设备编码流及其时间戳，支持 MP4/MKV 和无播放录制 | 借鉴启动体验、诊断指标、录制架构；Android 的息屏控制、虚拟显示、启动 App 等不能直接套到 iOS |
| [QtScrcpy](https://github.com/barry-ran/QtScrcpy) | 图形化配置、键位脚本、多设备、后台录制、复制粘贴 | 改进键位预设复用和多设备操作。README 同时宣传 QuickMirror/QuickAssistant，应区分这些独立产品的能力 |
| [UxPlay](https://github.com/FDH2/UxPlay) | AirPlay PIN/密码、允许/拒绝列表、BLE beacon 发现、可配置同步策略及 RTP 输出 | 最适合评估上游能力整合。你已经集成 UxPlay，不应把“接入 UxPlay”当作新建议 |
| [Reflector](https://www.airsquirrels.com/reflector) | 多设备自动布局、突出指定设备、连接时确认、屏幕连接码 | 学习多设备管理和接入体验。其“Device Control”页面主要指显示管理，不是 iPhone 触控注入 |
| [AirServer](https://www.airserver.com/PC) | AirPlay、Google Cast、Miracast 接收，多设备展示 | 如果扩展到会议/教育市场，可研究多协议；对于当前 Windows+iPhone 定位，投入明显较大 |
| [都玩投屏](https://douwan.video/) | 插线即投、裁剪显示区域、虚拟摄像头和直播工具集成 | 借鉴连接流程和输出裁剪；其“都玩相机”是另有移动端 App 的产品，不能把 4K 相机采集视为现有镜像协议顺手可得的能力 |
| [傲软投屏](https://www.apowersoft.cn/phone-mirror) | 图形化操作、画笔演示、设备多开、面向不同使用场景的入口 | 学习场景入口和引导。官网不同平台的功能范围不同，不能默认全部适用于 iOS |

竞品宣传的“零延迟”“35–70 ms”“128 台”等数值未在统一环境验证，且都玩官网不同区块的设备数量口径并不一致；本报告不据此断言性能优劣。

## 三、建议优先级

| 优先级 | 建议 | 主要收益 | 相对工作量 |
|---|---|---|---|
| P0 | 连接健康面板 + 脱敏诊断包 | 用户能定位卡在哪一步，维护者能直接分析 | 中 |
| P0 | 真机兼容性和反复连接回归矩阵 | 把连接成功率和反控稳定性变成可追踪指标 | 持续投入 |
| P1 | 多设备自动排布 + 场景保存 | 多机和直播用户每天都会受益 | 中 |
| P1 | 可靠录制模式 | 减少长录制意外丢失 | 中 |
| P1 | 官方 MCP 适配器 + 配置导出 | 让现有 API 更容易被 AI 和自动化客户端使用 | 中 |
| P2 | 输出区域裁剪 | 竖屏内容、直播和演示更方便 | 中；与反控同时使用时更高 |
| P2 | AirPlay PIN/接入确认 | 教室、会议等共享网络中更可控 | 中至高，依后端能力而定 |
| P2 | 音频电平、监听设备和同步偏移 | 改善直播与录制音频体验 | 中 |
| P3 | 最近 30/60 秒回放保存、截图 OCR | 有明确场景时再做 | 中至高 |
| 研究项 | USB 编码流直接封装 / GPU 输出优化 | 降低录制负载，减少重复处理 | 高 |

### 1. 连接健康面板与脱敏诊断包

**现有基础**：`SetupAssessment`、驱动检查、实时日志、反控状态窗口、API 能力信息和原生日志已有大量证据，缺的是统一呈现与便捷导出。

建议最小版本：

- 按设备显示四条独立状态：设备发现、画面采集、音频、反向控制。支持“可以投屏，但反控未就绪”的真实状态。
- 将信任、开发者模式、DDI、蓝牙外设角色和无线发现检查汇总；每项显示检查结果及下一步操作。
- 导出最近一段日志、版本、系统、设备型号、驱动摘要和检查时间线。复用并补充现有脱敏逻辑，导出前可预览；不附带配对文件、密钥、手机截图或剪贴板内容。
- 记录用户感知指标：点击连接到首帧时间、最近恢复次数；将接收帧率、解码耗时、队列等待和呈现帧率分开显示。

**指标边界**：当前已有 FPS、latency 字段及解码/呈现时序日志，不需要从零开始。`接收→Present` 是 Windows 侧链路指标；解码耗时也不能叫“手机到显示器总延迟”。端到端延迟需要单独的测量方法。

**验收示例**：当没有画面时，诊断能区分“驱动预检通过但握手未收到帧”和“已经收到帧但解码/显示异常”，而不是统一建议重装驱动。

### 2. 兼容性与恢复：作为产品能力持续交付

2026-10-23 查询的公开问题包括：[#65 二次有线投屏停在握手](https://github.com/RayrenSX/iPhoneMirror/issues/65)、[#64 新系统蓝牙反控卡死](https://github.com/RayrenSX/iPhoneMirror/issues/64)。这些是用户报告，不是本次复现结论；工作区也已有相关恢复及蓝牙修复，仍需用最终发布包验收。

建议将现有路线图里的测试矩阵落成可查看的兼容性表：机型、iOS、Windows、Apple 组件、投屏模式、反控方式，以及“自动检查通过/真机验证通过”的区别。优先覆盖连续开始停止、拔线重连、锁屏解锁、长时间控制、双设备独立停止等组合。

驱动修复仍复用独立管理器；新诊断面板负责给出证据和准确入口，不应看到超时就自动重装驱动。

### 3. 多设备自动排布与场景预设

**参考**：[Reflector 的 Smart Layouts 与 Emphasize Devices](https://www.airsquirrels.com/reflector/features/device-control)。

当前已有设备绑定和部分按设备保存的画质偏好。建议扩展为用户可命名的“日常办公”“双机对比”“竖屏直播”场景：

- 保存设备对应关系、窗口尺寸/位置、所在显示器、旋转、置顶、静音及画质预设。
- 提供左右对比、网格、主设备加辅助设备三种排布；第一版只调整现有窗口，不必建设视频合成器。
- 对缺失设备、显示器变化和 DPI 变化进行降级处理，保证恢复后的窗口可见。
- 单独提供键位预设导入导出；按设备比例/方向验证坐标，避免盲目套用。

不在预设文件中明文携带推流密钥、API 密钥或设备配对资料。恢复场景默认恢复布局和参数，录制、直播及控制的自动启动单独设计。

**验收示例**：两台手机断开并重新连接后，用户选择“双机对比”，即可恢复对应窗口和音频偏好；显示器拔掉后窗口落在可见屏幕内。

### 4. 可靠录制模式

**现有基础**：输出已支持硬件编码、音画节奏处理、录制与直播并行，以及结束后尚未保存的录制重新提示。`PendingRecordingStore` 解决的是待保存文件管理，不能等同于未完成 MP4 的崩溃恢复。

当前录制参数包含 MP4 `+faststart`；这不等于异常断电后仍可完整恢复。

最小版本建议：

- 增加可靠录制选项，评估 MKV 或分段/碎片化 MP4；完成后可另存为常用 MP4。
- 支持按时长或体积分段、剩余磁盘空间检查、失败时保留可恢复部分。
- 程序重启时扫描未完成任务，明确显示“可保存的完整片段”与“需要恢复的片段”。

参考 [scrcpy 录制文档](https://github.com/Genymobile/scrcpy/blob/master/doc/recording.md)。容器改变仍需处理音画时间戳和横竖屏/分辨率变化，不能只替换文件后缀。

**验收示例**：长录制中强制结束进程，重启后能够保存此前已完成的片段，并清楚说明最后一段是否受损。已有录制/推流并行行为保持正常。

### 5. 官方 MCP 适配器与自动化体验

**现有基础**：[API 文档](api/README.md)明确说明仓库尚未包含独立 stdio MCP 服务；已有 HTTP API、鉴权、权限、设备能力、截图和独占控制租约，应直接复用。

建议第一版提供设备列表、状态、截图、点击、滑动、输入文本、收回/释放控制等薄封装，以及“生成客户端配置”入口。实现放在独立工具目录，不需要再建设设备管理器。

适配器需遵守现有约束：截图坐标与 geometryVersion、操作前获取控制租约、结束时释放、设备断线后不自动重放输入、按设备真实能力暴露工具。已存在的外部适配器可优先整合或复用。

后续再评估状态事件订阅（SSE 或 WebSocket）和帧订阅，减少轮询。HTTP 截图限频不能直接改成高帧率视频传输；需设计独立有界订阅，并继续保持本地 API 默认边界。

### 6. 输出裁剪

**参考**：[都玩投屏官网功能表](https://douwan.video/)列有裁剪显示区域。

第一版建议仅为录制、推流、虚拟摄像头添加一个共享矩形裁剪区，保留完整预览供操作，并显示裁剪结果预览。这样能直接服务竖屏直播、只展示指定 App 区域等场景。

如以后加入“裁剪后的画面直接反控”，必须统一裁剪、旋转、缩放与触控坐标映射，不能只裁显示画面。裁剪也不应改变现有 API 的原生截图坐标约定。

此项与自定义图片叠加层不同，但仍建议独立评估产品范围；不借此加入复杂场景编辑器。

### 7. AirPlay 接入策略与发现改进

**参考**：[Reflector 接入确认和屏幕码](https://www.airsquirrels.com/reflector/features/security)、[UxPlay 的 PIN/密码与设备列表选项](https://github.com/FDH2/UxPlay)。

当前检查的主程序与宿主配置未见用户可设置的统一接入策略。可以先验证 UxPlay 后端的 PIN/密码整合，再决定默认后端如何支持，界面明确标注各后端能力；不要默认两个后端都能实现相同策略。

UxPlay 还提供 Windows BLE beacon 发现方式，值得做单独原型：它可能改善不支持常规 DNS-SD 发现的环境，但不能解决 Wi-Fi 客户端隔离或媒体端口被阻断。还需验证与现有 BLE HID 反控共用适配器时的表现。

### 8. 音频工具与后续探索

- **音频电平与监听设备选择**：来源和麦克风分别显示电平，添加明确的监听输出设备，避免直播中反复修改 Windows 默认设备。
- **同步偏移**：为输出提供可调的音视频偏移；用长录制和切换设备验证漂移，不只验证开始时同步。
- **回放缓存**：在可靠分段录制基础上，增加保存最近 30/60 秒，限制缓存磁盘占用。不是长期缓存原始 NV12 帧。
- **截图 OCR**：只针对用户主动选定的画面识别文字，先验证 Windows OCR 语言包和中文效果；它是便利工具，不是 iOS 可访问性树。
- **编码流直封装**：当前输出从解码帧读取 NV12 再交给 FFmpeg 编码；可研究 USB 在不缩放、不裁剪时直接封装设备编码流。需要新增压缩数据输出、时间戳和格式切换处理；无线现有 IPC 主要输出解码帧，不能假设可以直接复用。

## 四、暂不优先扩展的范围

- 自定义图片叠加层：仓库 [Issue #51 处理记录](issues/51-custom-stream-overlay.zh-CN.md)明确记载 2026-10-11 决定不实现。本报告不将它列为推荐新增。
- 完整视频编辑器、云端远控和账号体系：增加维护面，当前主链路和自动化体验的收益更直接。
- 整套跨平台 UI 重写：现有 WPF、D3D11、WASAPI 和驱动链路与 Windows 绑定较深；已有社区移植可先共享协议和兼容性信息。
- 直接照搬 Android 息屏投屏、虚拟显示和 App 启动：需要独立证明 iOS 服务或协议支持。
- “手机相机直出 4K”：若没有对应协议，通常需要额外手机 App，应该作为独立产品方向评估。

## 五、落地顺序与发布建议

1. 先把近期蓝牙、握手恢复、更新和音频改动放进最终包进行真机验收；记录兼容性结果。
2. 交付连接健康汇总与脱敏诊断包，同时将已有性能日志整理成有明确含义的指标。
3. 交付多设备排布和场景保存；将已有“关闭主窗口到托盘”列入发布说明与验收，不再重复开发。
4. 按主要用户选择可靠录制或 MCP 集成，再考虑输出裁剪、接入策略和音频工具。

文档上也值得先做一次对齐：当前 [路线图](ROADMAP.md)和[架构说明](ARCHITECTURE.md)仍以 2026-10-01 的 `1.8.4-test4` 为基线，而工作区及变更记录已包含更新能力。明确“已发布 / 工作区已实现 / 待真机验证 / 计划中”，比继续扩大泛化功能列表更能帮助用户判断。

商业 Windows 签名已在现有路线图中，属于发布体验改进而非新功能；可与上面的功能迭代并行推进。

本次仅新增调研文档，未更改功能代码，也未声称完成竞品或本项目的实机性能测试。
