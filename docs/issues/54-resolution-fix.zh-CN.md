# Issue #54：iPad 原生分辨率的修复与验收

> 文档整理说明（2026-11-05）：文中构建产物、日志和截图的本地记录路径不随仓库分发，保留用于追溯；历史测试结论未在本次重新执行。

对应 [#54](https://github.com/RayrenSX/iPhoneMirror/issues/54)。本记录区分已有的本地候选修复与仍待目标设备实测的输出能力，不代表已发布或已完成原生分辨率支持。

**最新复审（2026-10-17）**：此前 B 原生补丁仍保持撤回。后续实测推翻了
“Stevenote 内容不能旋转”的判断：内容会转动，但方向附件始终为零。
新的候选通过共存 USB 查询系统方向，已得到正确转正的原生横竖屏截图，
竖屏启动后四方向验收通过（5085 帧、无重连、正常退出），横屏启动降档也已通过
USB 专用 4096×4096 能力修正，两次横屏直接启动取得 2360×1640，最终轮自动旋转通过。
无线 iPad 专用 2360 对称档已实测达到 `1640×2360 → 2360×1640 → 1640×2360`。
普通 B 已接入逐帧方向元数据，修复版正常竖屏、左右横屏、恢复竖屏均已实机转正。
该旋转验收不代表 B 已达到原生分辨率；实测仍为 `1000×1440 ↔ 1440×1000`。
详见文末复审记录。Issue 附件中的 iPad8,11 仍待同机验证。

## 已确认的代码问题

旧版只有少数 ProductType 的面板映射，未知 iPad 一律请求 1640×2360。
2018 款 12.9 英寸 iPad Pro 的 `iPad8,5`、`iPad8,6`、`iPad8,7`、`iPad8,8`
应为竖屏 **2048×2732**、横屏 **2732×2048**。Issue 正文的 2360×1640
对应其他尺寸的 iPad，不能作为该型号的验收目标。

当前工作区已有 `src/Core/src/Capture/UsbDisplaySize.h` 的精确型号映射，A/B 模式
默认请求对应尺寸；未知型号仍走兼容回退，日志通过 `display_size_source=model/fallback`
区分。`CoreTests.cpp::test_usb_projection_modes` 覆盖上述四个变体、其他面板和未知型号。

源码未发现将 USB 源流统一限制为 1600×1200 的硬编码。C 模式明确使用 1565×1565
的兼容请求；普通画质设置限制的是本地渲染尺寸，帧率设置也不会强制源流分辨率。

## 本次说明修正

高级设置实际已支持手动请求，但此前四语言说明未写明仅 B 模式生效，且错误描述为
覆盖普通画面预设。现在明确适用模式、面板尺寸示例及实际输出验收口径，并同步用户指南。
本次没有新增协议模式或修改既有 A/B/C 协商行为。

## 目标设备的验证步骤

1. 记录准确 ProductType、iPadOS 版本和所用应用版本。确认测试包包含上述映射修正。
2. 解锁设备，保持竖屏，在同一静态文字画面比较 A、B 默认请求；C 只作兼容对照。
   画面设置选择“原生（不限制渲染尺寸）”。
3. 停止投屏，选择 B 模式，连续点击主窗口版本号五次启用高级设置，输入宽 2048、
   高 2732（按字段名称，界面先显示高度），应用后重新开始投屏。
   显式自定义宽高会跳过将首批竖屏解码尺寸用作后续请求的探测分支，适合比较默认协商。
4. 分别记录竖屏和横屏的请求尺寸、`video_output width/height`、实际分辨率、帧率和
   稳定性。`usb_projection display_size` 只是请求，不能作为成功证据。
5. 若仍输出 1200×1600 / 1600×1200，保留请求与解码日志，继续研究该 iPadOS 的
   编码档位和 HPD1 参数。关闭高级模式可回到默认协商；尚不能把型号表修正标为问题完全解决。

不要直接把 `request_native_display_size` 设为 true 当成修复：它会从 HPD1 中省略
`DisplaySize`，而现有协议测试和说明要求保留该字段以启动视频，尚无该设备的成功证据。

## 验收边界

面板映射和协议测试只能证明请求正确。只有目标设备实际解码输出达到
2048×2732 / 2732×2048，且横竖屏、帧率与稳定性通过，才能宣称该型号支持原生分辨率。
预览放大、截图插值或新增名为“原生”的开关都不满足此条件。

## 本次验证（2026-10-15）

- `CoreProtocolTests` 通过，包含上述型号映射与 A/B/C 模式协商回归。
- 四语言资源校验通过，App 每语言 1599 个键，驱动管理器每语言 199 个键。

`CoreMedia.cpp::parse_format_description` 从设备的 `vdim` 读取宽高；
`MediaFoundationDecoder.cpp` 将其写入解码输入的 `MF_MT_FRAME_SIZE`，其配置日志也打印
同一格式的宽高。`CaptureSession.cpp` 的会话状态直接读取 `protocol.video_format()`。
这三处与附件日志互相印证，定位到设备给出的源格式已经为 1440×1080，
不支持将本次问题归因于 Windows 预览缩放或解码器主动降低分辨率。

`native_size=false` 指没有进入“省略 DisplaySize”的协议分支，不代表程序启用了
1080p 上限。`QuickTimeSession.cpp::make_hpd1` 在该分支正常编码请求的 Width/Height。
“原生”画质的 `resolution=0x0` 则表示取消本地渲染尺寸上限，不会强制设备编码器使用
面板像素。型号映射与高级输入只能改变请求，不能证明设备接受了对应编码尺寸。

### 自动重连和首帧探测

12:13:40.833、12:13:56.808 各触发一次 `frame_rate_unavailable` 快速重连。
两次均为视频约 5 秒未更新、音频仍在持续；仅凭日志无法区分静态画面按需停帧与异常停帧。
重连后的解码器配置仍为 1440×1080。第一帧低分辨率早于两次重连，
所以重连不是首次降分辨率的原因。

本次指定了自定义宽高，源码的首批竖屏帧探测要求两个自定义值都为零，因此不会触发。
附件也没有 `display valeria_probe` 或 `display reconfigure` 记录。
`adaptive=true` 不能单独作为实际发生过重配、或重配覆盖自定义请求的证据。

### 定位结论和待验证条件

已定位为 **B 模式 `Valeria=false + DisplaySize=2732×2048` 未协商出面板原生源流**。
此前面板映射修正和手动输入尺寸不足以解决这次反馈。当前附件没有设备 iPadOS 版本、
A 模式对照或成功的原生输出记录，仍不能确定具体编码档位选择规则，也不能宣称
该设备硬件或系统的 USB 编码上限固定为 1440×1080。

下一轮应在同一设备、同一系统、同一持续变化的测试画面下对照：

1. A 模式默认面板请求（2048×2732，Valeria=true）。
2. B 模式关闭高级自定义（2048×2732，Valeria=false）；注意首帧探测可能随后重配，
   须区分首次格式与重配后的格式。
3. B 模式显式输入宽 2048、高 2732，分别在竖屏与横屏启动；与本次 2732×2048 对照。

以上对照用于区分 Valeria、请求方向、默认探测与设备端编码策略的影响，
不应预先把宽高交换认定为根因。若仍均为低分辨率，需要成功的同设备 QuickTime
或其他 USB 客户端对照及协商 trace，才能进一步定位缺失的协议能力或参数。
本次仅检查远端附件与源码，没有在目标 iPad 上完成上述验证，也没有修改协商行为。

- 该设备具备通过当前核心输出原生像素的能力。A→B/C→A 对照中，A 两次均成功，

## 2026-10-17：B 模式修复与最终产物验证

> 本节是第一次候选修复的历史记录；随后旋转复审发现回归，测试补丁已撤回。

### 根因与诊断对照

只发送 `Valeria=false + DisplaySize` 时，iPad 进入普通非演示显示路径，
即使请求面板像素也可以选择低分辨率编码档位。A 的原生输出不能证明 B 配置充分。
针对接入的 iPad15,7 / iPadOS 26.5.2，隔离诊断构建逐项验证了以下组合：

| 新增能力 | 结果 |
| --- | --- |
| 仅 HEVCDecoderSupports444 | 仍为 1000×1440 H.264 |
| 仅 H264DecoderSupports444 | 仍为 1000×1440 H.264 |
| CameraPreview | 仍为 1000×1440 |
| 仅 Stevenote | 720×1036，返回当前核心不支持的编码格式，未通过解码；不能作为修复 |
| Stevenote + H264DecoderSupports444 | 返回原生 1640×2360 AVC 4:4:4；Windows H.264 MFT 无法解码 |
| 上述组合 + 配套 FFmpeg 软件解码 | 输出可见原生 1640×2360 帧，真实状态栏保留 |

`Stevenote` 是设备识别的显示用途标识。公开的设备端实现分析也显示 HPD1 中的
该键与 `H264DecoderSupports444` 分别影响端点和编码策略；这里以设备对照结果作为
修复依据，不将其他版本的实现分析等同于本机实测。

因此需要同时修复 **显示用途协商、接收端解码能力、实际解码实现**。
仅修改 `DisplaySize`、仅切换 HEVC 开关或把 Valeria 改为 true 都不能满足 B 模式的目标。

### 代码变化

1. iPad 的 B 模式在随包 AVC 4:4:4 解码器可用时发送
   `Valeria=false + Stevenote=true + H264DecoderSupports444=true + DisplaySize`。
   不启用演示状态栏；缺少解码组件时保留旧请求与解码链路。
2. 保留型号面板请求，不将已降采样的首帧认作 `probed_native` 再次请求。
3. 按竖向编码画布规范化自定义长短边：该设备仍使用竖向编码画布承载横屏内容。
   新协议下直接请求 2360×1640 会得到 1080×1554；规范化为 1640×2360 后恢复原生。
4. 从 AVC SPS 读取色度格式和位深；4:4:4 使用现有随包 FFmpeg 的 H.264 软件解码器，
   避免 Windows MFT 的 `ProcessOutput 0x80004005`。
5. 保留全部亮度像素和原范围，色度按 2×2 滤波转换到现有 NV12 呈现格式；
   没有放大图像。软件解码状态如实返回，不将其标为硬件解码。
6. FFmpeg 运行库仅从核心相邻的 `Wireless/` 加载，核验 ABI 与所需导出函数；
   沿用项目固定的 libavcodec 58 / libavutil 56 运行库及已有许可证。
   同步四语言模式说明，说明软件解码与外接视频播放行为差异。
