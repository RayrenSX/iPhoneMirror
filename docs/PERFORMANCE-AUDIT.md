## 已完成的优化

| 路径 | 原有开销 | 修改与约束 |
| --- | --- | --- |
| `MediaOutputService.FrameLatch` | 每次发布 NV12 帧都 `ToArray()`，持续产生大对象堆分配 | 改为生产、待消费、消费三个缓冲区轮换。复制在交换锁外进行，锁内仅交换引用。消费者在下一次 `Get()` 前独占当前帧，慢速管道不会读到覆盖中的数据。待消费帧只保留最新一帧。 |
| `materialize_gpu_frame` | 每次 GPU→CPU 读回都创建 staging texture | 复用一张暂存纹理，尺寸/格式变化时重建；沿用互斥保护。RAII 保证复制失败或分配异常时仍执行 Unmap 和 keyed-mutex 释放；设备丢失后清理缓存，允许下次重新创建。 |
| `QuickTime.StreamDecoder` | 每批 USB 数据先写入组包缓冲，再复制到包对象，并移动剩余数据 | 完整包直接从输入读取，仅复制到拥有独立生命周期的包对象。组包缓冲只保存当前未完成的包，先验证长度再追加数据。 |
| `DirectUsbInputBridge` | 触控、键盘、按钮和剪贴板消息先生成 UTF-16 JSON 字符串，再编码为 UTF-8 | 五处发送路径直接使用 `SerializeToUtf8Bytes`。继续使用相同的 JSON 字段、长度前缀和发送锁。 |

帧缓冲复用仍保留一次必要的像素复制，用于隔离原生复用数组与异步管道写入。
其容量最多为三个已分配帧缓冲；分辨率增大时会重新分配，预热后的零分配只适用于稳定尺寸。
`FrameLatch` 的契约是单生产者、单消费者，旧视图不可在下一次 `Get()` 之后继续使用。

## 实测

### 托管帧交接分配

使用实际 `FrameLatch` 处理 120 帧 1920×1080 NV12，先预热 8 次，再通过
`GC.GetAllocatedBytesForCurrentThread()` 测量同步发布/消费循环。与原 `ToArray()`
快照方式对比：

| 方式 | 120 帧累计分配 |
| --- | ---: |
| 原快照方式 | 373,250,880 字节 |
| 三缓冲复用，预热后 | 0 字节 |

按 60 帧/秒估算，这条路径可避免约 186.6 MB/秒的持续托管分配。
这不是整个录制流程的零分配承诺，也不是常驻内存减少 373 MB。

### USB QuickTime 解包

分别编译修改前保存的源码和当前源码，使用相同 MSVC Release `/O2` 设置。
每种输入累计处理 512 MiB，重复 7 次取中位数；两版输出校验和均为 `11654662656`。

| 输入 | 修改前 | 修改后 | 耗时下降 |
| --- | ---: | ---: | ---: |
| 完整 64 KiB 包 | 31.070 ms | 15.913 ms | 48.8% |
| 2 MiB 包按 64 KiB 分片 | 206.456 ms | 189.937 ms | 8.0% |
| 每批合并 64 个 1 KiB 包 | 95.269 ms | 82.328 ms | 13.6% |

这些是内存输入微基准，不包含 USB 驱动、真实传输、解码和屏幕呈现耗时。
GPU 纹理复用和 UTF-8 序列化未单独量化速度收益。

  端到端延迟、长时间音画同步及不同显卡驱动上的收益仍需这些场景确认。
